# 프로젝트 공통 명세

이 문서는 모든 모듈에 공통으로 적용되는 프로젝트 목표, 시뮬레이션 의미, 상태 정의, 평가 기준 및 초기 MVP 완료 조건의 단일 원본이다.

구체적인 표현 방식이나 아직 확정되지 않은 값은 임의로 채우지 않고 `project_decisions.md`에서 상태를 확인한다.

## 1. 프로젝트 목표와 범위

프로젝트의 목표는 택시 수요를 예측하고 택시를 동적으로 배차·재배치한 뒤, 동일한 조건의 기준 방식과 비교하여 공차 시간이 줄어드는지 검증하는 것이다.

초기 MVP의 범위는 다음과 같다.

- 3×3 블록으로 구성된 가상 도시
- 택시 3대
- 시간에 따라 발생하는 승객 호출
- 택시의 승객 픽업 및 목적지 이동
- 단순한 기준 수요 예측
- 예측 결과를 사용한 빈 택시 재배치
- 기준 배차 방식과 예측 기반 방식의 비교

초기 MVP는 예측 기반 방식이 항상 더 좋은 결과를 낸다고 전제하지 않는다. 동일한 조건에서 공차 시간 감소 여부와 그에 따른 서비스 지표 변화를 재현 가능하게 측정하는 것이 목표다.

## 2. 모듈 책임

### Module 1: 시뮬레이션

- 3×3 가상 도시, 도로, 블록, 구역과 좌표 체계 관리
- 택시 위치와 상태 관리
- 승객 호출의 런타임 발생과 상태 관리
- 픽업·탑승·하차 과정
- 택시 이동과 이동 시간 계산
- 배차·재배치 명령 실행
- 시뮬레이션 시간 진행
- 공차 시간과 승객 대기 시간 등 지표 기록

Module 1은 예측 모델과 배차 정책 내부에 직접 의존하지 않는다. 합의된 계약을 통해 결과와 명령을 전달받는다.

### Module 2: 데이터 처리

- 초기 MVP용 호출 시나리오 데이터 생성
- 실제 데이터 도입 시 적재와 정제
- 시공간 단위 집계
- 결측값과 이상값 처리
- 예측용 피처 생성
- 학습·검증·테스트 데이터 분리
- Module 3 입력 데이터 생성
- 데이터 스키마와 품질 검증

Module 2는 재현 가능한 호출 시나리오와 입력 데이터를 생성한다. Module 1은 이를 읽어 런타임 호출 이벤트와 상태를 생성하며 동일한 생성 규칙을 중복 구현하지 않는다.

### Module 3: 수요 예측

- 구역별 미래 수요 예측
- 예측 입력과 출력 형식 관리
- 모델 학습·검증·평가
- 예측 성능 지표 계산
- 학습된 모델 또는 기준 예측 방식 제공

### Module 4: 배차와 재배치

- 현재 택시 상태와 대기 호출 확인
- 승객 호출에 대한 택시 배차
- 예측 수요를 기반으로 한 빈 택시 재배치
- 기준 배차 정책과 예측 기반 정책 제공
- 배차 및 재배치 결정 기록

Module 3과 Module 4의 책임은 구분한다. 예측 모델을 바꾸지 않고 배차 정책을 비교하거나, 배차 정책을 바꾸지 않고 예측 모델을 비교할 수 있어야 한다.

## 3. 시뮬레이션 시간

모든 시뮬레이션 동작은 하나의 일관된 시뮬레이션 시계를 사용한다.

- 실제 컴퓨터의 현재 시각을 시뮬레이션 의사결정에 직접 사용하지 않는다.
- 호출 발생, 이동, 픽업, 하차, 예측, 배차 및 재배치는 같은 시간 기준을 사용한다.
- 실행 속도를 변경해도 같은 설정과 시드의 논리적 결과가 달라져서는 안 된다.
- 시간 단위와 동일 시각 이벤트의 처리 순서는 명시적으로 결정하고 기록한다.
- 시간 규칙을 변경하면 모든 관련 모듈, 계약과 테스트에 미치는 영향을 확인한다.

시간 단위와 이벤트 우선순위는 `project_decisions.md`에 확정되기 전까지 프로젝트 표준으로 추측하지 않는다. 임시 가정이 꼭 필요하면 적용 범위, 대안과 변경 비용을 먼저 밝힌다.

## 4. 좌표, 거리와 이동 시간

- 모든 모듈은 동일한 구역 ID, 좌표 기준, 거리 단위와 이동 시간 단위를 사용한다.
- 거리와 이동 시간 계산 방식은 공용 계약에 명시한다.
- 이동 시간은 음수가 될 수 없다.
- 택시 위치는 정의된 가상 도시 범위를 벗어날 수 없다.
- 거리 또는 이동 시간 계산을 변경하면 기준 방식과 예측 기반 방식에 똑같이 적용한다.

정확한 계산 방식은 `project_decisions.md`에서 관리한다.

## 5. 택시와 승객 호출 상태

택시 상태는 최소한 다음 상황을 구분할 수 있어야 한다.

- 승객 없이 대기 중
- 승객을 태우러 이동 중
- 승객을 태우고 이동 중
- 수요 예상 지역으로 재배치 중

승객 호출 상태는 최소한 다음 상황을 구분할 수 있어야 한다.

- 호출 발생
- 배차 대기
- 택시 배정
- 픽업 완료
- 이동 중
- 하차 완료
- 취소 또는 처리 실패

상태 변경은 명시적인 전이 규칙을 따라야 한다. 구현 전에 상태 전이표에 다음 정보를 기록한다.

| 항목 | 내용 |
|---|---|
| 현재 상태 | 전이 직전 상태 |
| 이벤트 | 전이를 발생시키는 사건이나 명령 |
| 다음 상태 | 허용되는 전이 결과 |
| 선행 조건 | 전이에 필요한 조건 |
| 실패 처리 | 잘못된 전이의 오류 처리 |

불가능한 상태를 자동 보정하거나 오류를 숨기지 않는다. 세부 상태 전이표의 표현 위치와 형식은 `project_decisions.md`에서 확정한다.

## 6. 공차 시간과 보조 지표

공차 시간은 최소한 다음 항목으로 구분하여 기록한다.

- 공차 대기 시간: 승객 없이 정차하여 호출을 기다린 시간
- 픽업 이동 시간: 배정된 승객을 태우러 승객 없이 이동한 시간
- 재배치 이동 시간: 예상 수요 지역으로 승객 없이 이동한 시간

전체 공차 시간에 포함되는 항목은 실험 전에 명시한다. 최종 산식이 확정되기 전까지 임의로 포함 범위를 변경하지 않는다.

공차 시간과 함께 가능한 범위에서 다음 지표를 확인한다.

- 승객 평균 대기 시간
- 승객 대기 시간의 중앙값 또는 상위 백분위수
- 처리한 승객 수
- 처리하지 못한 호출 수
- 택시별 공차 시간
- 택시별 승객 탑승 운행 시간
- 전체 이동 거리
- 공차 이동 거리
- 실차율

실차율은 다음과 같이 계산한다.

```text
실차율(%) = (승객 탑승 운행 시간 / 총 택시 운행 가능 시간) × 100
```

- `승객 탑승 운행 시간`은 모든 택시가 승객을 태운 상태로 운행한 시간의 합이다.
- `총 택시 운행 가능 시간`은 실험에 참여한 모든 택시의 전체 가용 시간의 합이다.
- 기준 방식과 예측 기반 방식에 동일한 계산 기준을 적용한다.
- 실차율 개선폭은 `예측 기반 방식 실차율 - 기준 방식 실차율`로 계산하고 `%p`로 표시한다.
- 상대 개선율을 표시할 경우 `%p` 개선폭과 혼동되지 않도록 구분한다.

특정 지표를 개선하기 위해 다른 중요한 지표를 숨기거나 제외하지 않는다.

## 7. 공정한 비교 실험

기준 방식과 예측 기반 방식은 가능한 범위에서 다음 조건을 동일하게 유지한다.

- 승객 호출 시나리오와 발생 시각
- 승객의 출발지와 목적지
- 초기 택시 위치와 택시 수
- 도시와 도로 구조
- 이동 시간 또는 교통 조건
- 시뮬레이션 기간
- 난수 시드
- 평가 지표와 계산 방식

비교 대상의 차이는 실험에서 확인하려는 예측, 배차 또는 재배치 정책으로 제한한다.

결과를 보고할 때 평균값만 제시하지 않고 가능한 범위에서 실행 횟수, 시드, 변동성과 실패 여부를 함께 기록한다.

기준 배차 정책이 확정되기 전까지 특정 정책을 표준으로 가정하지 않는다.

## 8. 재현성

- 난수를 사용하는 구성요소는 명시적인 시드를 받는다.
- 호출 생성과 알고리즘의 난수 흐름은 가능한 범위에서 분리한다.
- 초기 위치, 시뮬레이션 기간과 정책 설정을 기록한다.
- 입력 데이터와 설정의 버전을 식별할 수 있게 한다.
- 결과에 사용한 코드 버전 또는 커밋을 추적할 수 있게 한다.
- 동일 시나리오를 기준 방식과 예측 기반 방식에 재사용한다.
- 결과만 남기고 실험 조건을 누락하지 않는다.

재현성을 깨뜨릴 수 있는 변경은 기능이 정상 동작하더라도 별도로 검증한다.

## 9. 미래 데이터 유출 방지

수요 예측과 배차 결정에는 해당 의사결정 시점에 실제로 알 수 있는 정보만 사용한다.

다음 행위를 금지한다.

- 예측 시점 이후에 발생한 실제 호출을 입력 피처에 포함
- 전체 데이터로 전처리 기준을 계산한 뒤 과거 학습 구간에 적용
- 미래 구간의 결측값이나 이상값을 결과를 본 뒤 처리
- 테스트 결과를 반복 확인하며 모델이나 기준값을 조정
- 아직 발생하지 않은 실제 호출을 배차 정책이 직접 참조
- 시뮬레이터가 가진 미래 이벤트를 예측·배차 모듈에 노출

데이터는 시간 순서를 고려하여 학습·검증·테스트 구간으로 분리한다. 전처리 통계는 학습 구간에서만 계산한다.

## 10. 구현 복잡도 원칙

먼저 단순한 기준 예측과 기준 배차로 전체 흐름을 작동시킨다. 측정 가능한 필요와 기대 효과가 있을 때만 더 복잡한 방법을 제안한다.

초기 MVP에서 자동으로 도입하지 않는 예시는 다음과 같다.

- 대규모 딥러닝 모델
- 강화학습 기반 배차
- 실시간 분산 처리 시스템
- 불필요한 마이크로서비스
- 외부 메시지 브로커
- 복잡한 3D 엔진
- 실제 교통 API
- 대규모 클라우드 인프라
- 일반화가 확인되지 않은 과도한 추상화

단순한 구현도 입력, 출력, 상태 전이, 오류 처리와 평가 기준이 명확해야 한다.

## 11. 기록과 관측 가능성

다음 주요 이벤트를 추적할 수 있어야 한다.

- 호출 발생
- 택시 배정
- 픽업과 하차
- 배차 실패
- 예측 실행과 결과
- 재배치 결정, 시작과 완료
- 택시와 호출 상태 변경
- 실험 시작과 종료
- 최종 평가 지표

기록에는 가능한 범위에서 시뮬레이션 시각과 관련 객체 ID를 포함한다. 특정 외부 관측 도구는 별도 결정 없이 도입하지 않는다.

## 12. 초기 MVP 완료 조건

초기 MVP는 최소한 다음 조건을 만족해야 한다.

- 3×3 가상 도시가 일관된 좌표 또는 구역 체계로 표현된다.
- 택시 3대의 위치와 상태를 추적할 수 있다.
- 승객 호출이 시뮬레이션 시간에 따라 발생한다.
- 택시가 호출을 배정받아 픽업하고 목적지까지 이동한다.
- 단순한 기준 배차 정책을 실행할 수 있다.
- 미래 수요를 예측하거나 추정하는 기준 방식이 존재한다.
- 예측 결과에 따라 대기 택시를 재배치할 수 있다.
- 동일한 호출 시나리오로 기준 방식과 예측 기반 방식을 비교할 수 있다.
- 공차 대기, 픽업 이동과 재배치 이동 시간을 구분하여 측정할 수 있다.
- 승객 대기 시간과 처리 건수를 함께 측정할 수 있다.
- 난수 시드와 실험 설정을 기록하고 결과를 재현할 수 있다.
- 미래 실제 정보가 예측이나 배차 결정에 노출되지 않는다.
- 모듈이 공용 계약을 통해 통합된다.
