# Git 브랜치와 커밋 규칙

이 문서는 저장소 전체에 적용되는 기본 Git 작업 규칙을 정의한다. 하위 디렉터리에 더 가까운 `AGENTS.md`가 별도 규칙을 정의하면 해당 범위에서는 하위 규칙을 우선한다.

## 1. 기본 원칙

- `main`과 `develop`을 사용하는 2브랜치 흐름을 사용한다.
- `main`은 검증이 완료된 안정 상태와 배포·발표 기준을 유지한다.
- `develop`은 다음 `main` 반영을 준비하는 기본 통합 브랜치다.
- 일반 개발 브랜치는 최신 `develop`에서 만들고 완료 후 `develop`으로 병합한다.
- 기능, 수정, 문서 또는 인프라 작업은 목적별 단기 브랜치에서 진행한다.
- 브랜치 하나는 하나의 작업 목적을 가진다.
- 커밋 하나는 설명 가능한 하나의 변경 단위를 가진다.
- 서로 무관한 변경을 같은 브랜치나 커밋에 섞지 않는다.
- 공용 계약 변경은 관련 문서, 생산자, 소비자와 계약 테스트를 함께 고려한다.
- 명시적인 요청 없이 브랜치 생성, 커밋, 푸시, 병합 또는 Pull Request 생성을 하지 않는다.

## 2. 브랜치 이름

기본 형식은 다음과 같다.

```text
<type>/<scope>-<summary>
```

- `type`과 `scope`는 영문 소문자로 작성한다.
- `summary`는 한국어 또는 영어로 작성할 수 있다.
- 공백 대신 하이픈을 사용한다.
- 작업 목적을 식별할 수 있도록 짧고 구체적으로 작성한다.
- 같은 브랜치에서 서로 무관한 모듈 작업을 함께 진행하지 않는다.

기본 `type`은 다음과 같다.

| type | 용도 |
|---|---|
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 변경 |
| `test` | 테스트 추가·수정 |
| `refactor` | 동작을 바꾸지 않는 구조 개선 |
| `chore` | 저장소 관리와 기타 작업 |
| `ci` | CI 설정 변경 |

기본 `scope`는 다음과 같다.

| scope | 대상 |
|---|---|
| `module1` | 시뮬레이션 |
| `module2` | 데이터 처리 |
| `module3` | 수요 예측 |
| `module4` | 배차와 재배치 |
| `contracts` | 공용 계약 |
| `integration` | 모듈 통합 |
| `docs` | 프로젝트 공용 문서 |
| `ci` | CI 설정 |
| `repo` | 저장소 전체 설정과 구조 |

예시는 다음과 같다.

```text
feat/module1-simulation-core
feat/module3-수요-예측
fix/module2-time-order
docs/contracts-호출-데이터
test/module4-duplicate-dispatch
chore/repo-tooling
```

## 3. 커밋 메시지

Conventional Commits의 간단한 형식을 사용한다.

```text
<type>(<scope>): <subject>
```

- `type`과 `scope`는 영문 소문자로 작성한다.
- `subject`와 본문은 한국어 또는 영어로 작성할 수 있다.
- 제목 끝에 마침표를 붙이지 않는다.
- 무엇을 했는지보다 변경 결과가 드러나도록 간결하게 작성한다.
- 변경 이유나 영향이 제목만으로 분명하지 않으면 본문에 설명한다.
- 이슈 번호가 있다면 본문이나 footer에 기록한다.

예시는 다음과 같다.

```text
feat(module1): 택시 상태 전이 구현
docs(contracts): 호출 데이터 공용 필드 정의
test(module4): 중복 배차 방지 검증 추가
fix(module2): 시간순 데이터 분할 오류 수정
chore(repo): 프로젝트 초기 구조 구성
```

본문이 필요한 경우 다음처럼 작성한다.

```text
fix(module2): 시간순 데이터 분할 오류 수정

검증 데이터가 학습 데이터보다 앞선 시점을 포함하지 않도록
분할 기준을 호출 발생 시각 기준으로 변경했다.
```

## 4. 커밋 분리

다음 기준으로 커밋을 분리한다.

- 기능 구현과 무관한 대규모 정리를 분리한다.
- 독립적으로 되돌릴 수 있는 변경은 가능한 범위에서 분리한다.
- 테스트가 구현과 하나의 원자적 변경을 이루면 같은 커밋에 포함할 수 있다.
- 공용 계약과 그에 따른 생산자·소비자 변경은 저장소가 중간에 깨지지 않도록 함께 묶거나 안전한 순서로 나눈다.
- 자동 포맷으로 많은 파일이 바뀌면 기능 변경과 분리한다.
- 커밋을 나누기 위해 불완전하거나 실행 불가능한 상태를 의도적으로 남기지 않는다.

## 5. Pull Request와 병합

- 일반 작업의 Pull Request 대상은 `develop`이다.
- `develop`에는 기능·수정·문서 작업의 검증이 완료된 변경만 병합한다.
- `main`에는 통합 검증을 마친 `develop`의 변경만 병합한다.
- Pull Request 하나는 하나의 작업 목적을 가진다.
- Pull Request 제목은 커밋 메시지와 같은 `<type>(<scope>): <subject>` 형식을 사용한다.
- 변경 내용, 이유, 영향 범위와 검증 결과를 Pull Request에 기록한다.
- 기본 병합 방식은 squash merge로 한다.
- squash된 최종 커밋 제목도 동일한 커밋 메시지 형식을 따른다.
- 첫 저장소 구성처럼 이력 자체가 없는 초기 작업은 사용자 합의에 따라 `main`에 직접 커밋하고 같은 커밋에서 `develop`을 생성할 수 있다.
- 긴급 수정으로 `main`에서 직접 분기했다면 수정 내용을 `develop`에도 반영하여 두 브랜치가 어긋나지 않게 한다.

## 6. 하위 디렉터리별 규칙

각 모듈이나 하위 디렉터리는 자체 `AGENTS.md`에서 해당 범위의 Git 규칙을 별도로 정할 수 있다.

하위 `AGENTS.md`에서 정할 수 있는 예시는 다음과 같다.

- 추가로 허용하는 `type`
- 해당 폴더에서 사용할 세부 `scope`
- 브랜치 이름의 추가 구성요소
- 커밋을 분리하거나 묶는 기준
- 커밋 전 필수 테스트나 검증
- Pull Request 제목과 설명에 포함할 추가 정보

적용 원칙은 다음과 같다.

- 가장 가까운 하위 `AGENTS.md`의 규칙을 우선한다.
- 하위 규칙은 해당 디렉터리와 그 하위 경로에만 적용한다.
- 상위 규칙과 다른 점과 적용 범위를 명확히 적는다.
- 하위 규칙이 없으면 이 문서의 기본값을 따른다.
- 하위 규칙에서도 `type`과 `scope`는 영문으로 작성한다.
- 저장소 전체에 영향을 주는 `main`·`develop` 운영, 병합 또는 릴리스 정책을 바꾸려면 루트 공용 문서를 갱신한다.

하위 `AGENTS.md`의 예시는 다음과 같다.

```markdown
# Module 3 작업 규칙

## Git 규칙

- 이 디렉터리의 기본 scope는 `module3`이다.
- 모델 실험만 변경하는 브랜치는 `experiment/module3-<summary>`를 사용할 수 있다.
- `experiment` 커밋은 재현 가능한 설정과 평가 결과를 함께 기록한다.
- 커밋 전에 Module 3 테스트와 관련 계약 테스트를 실행한다.
```

## 7. 초기 커밋

현재처럼 저장소에 기존 커밋이 없는 초기 구성은 다음 메시지를 사용할 수 있다.

```text
chore(repo): 프로젝트 초기 구조 및 공통 규칙 구성
```

실제 커밋 전에는 포함 파일, 민감정보, 대용량 데이터와 생성물을 다시 확인한다.
