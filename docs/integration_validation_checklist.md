# 통합 검증 체크리스트

이 문서는 각 MVP 또는 기능 확장 단계가 끝난 뒤 종단 통합 검사를 설계할 때 사용하는
공통 점검표다. 매 실험 보고서에 반복해서 출력하거나 알고리즘 성능의 합격 기준으로
사용하지 않는다.

현재 구현의 고정된 맵 크기, 구역 수, 택시 수와 호출 수를 영구 조건으로 가정하지 않는다.
각 통합 검사에서는 해당 단계의 설정과 공용 계약을 기준으로 대상 집합을 결정한다.

## 1. 검사 시점

- 초기 MVP 또는 다음 MVP의 구현 범위가 모두 합쳐졌을 때
- 공용 계약, 시간 기준, 좌표·구역 체계 또는 상태 전이가 변경됐을 때
- 예측 입력·출력이나 배차·재배치 명령 계약이 변경됐을 때
- 비교 실험 또는 릴리스 후보를 확정하기 전

## 2. 실행 조건 기록

- 사용한 코드 버전 또는 커밋
- 시나리오 설정, 난수 seed와 평가 구간
- 맵·구역 구성, 택시 수와 호출 생성 조건
- 사용한 예측 모델과 배차·재배치 정책
- 비교군 사이에서 의도적으로 다르게 둔 항목

## 3. 비교 공정성

- 비교 정책은 같은 과거와 같은 숨겨진 미래 호출을 사용한다.
- 초기 택시 상태, 맵, 시뮬레이션 시간과 종료 조건이 같다.
- 비교하려는 모델 또는 정책 이외의 설정은 같다.
- 같은 seed와 설정을 다시 실행하면 같은 입력 시나리오가 생성된다.

## 4. 시간과 미래 정보 경계

- 예측 시각 이후의 실제 호출은 현재 관측과 피처에 포함되지 않는다.
- 예측 시각의 호출은 계약에서 정한 반개구간 경계에 따라 처리된다.
- 같은 과거에 서로 다른 미래를 붙인 두 실행은 예측 시각까지 관측, 피처, 예측과
  의사결정 결과가 같아야 한다.
- 미래 필드를 입력에 강제로 넣으면 조용히 사용하거나 보정하지 않고 실패해야 한다.

권장 검사는 동일한 과거를 가진 시나리오 A와 B의 미래만 다르게 만든 뒤 예측 시각에서
다음을 비교하는 방식이다.

```python
assert observation_a == observation_b
assert features_a == features_b
assert forecasts_a == forecasts_b
assert plan_a == plan_b
```

## 5. 공용 계약과 상태 일관성

- 생산자의 공개 출력이 별도 변환 없이 다음 모듈의 공개 입력으로 전달된다.
- 설정된 전체 대상 구역 또는 공간 단위에 필요한 출력이 존재한다.
- 명령은 존재하는 택시, 호출과 유효한 목적지만 참조한다.
- 같은 택시나 호출을 한 결정에서 모순되게 중복 사용하지 않는다.
- 택시와 승객 상태 전이가 공용 계약과 일치한다.
- 정상 입력으로 생성한 내부 명령이 실행 단계에서 거부되지 않는다.

## 6. 지표 무결성

- 시간·거리 구성요소의 합이 전체 측정값과 일치한다.
- 완료, 대기, 탑승과 미처리 호출 수가 시나리오 상태와 일치한다.
- 기준 정책과 실험 정책이 같은 정의와 단위로 측정된다.
- 결과에는 예측값, 실제값, 정책 결정과 핵심 운행 지표가 함께 남는다.

## 7. 단계별 완료 조건

구체적인 성능 목표와 기능 시나리오는 해당 MVP 계획에서 별도로 정한다. 예측 정책이
모든 시나리오에서 기준 정책보다 좋아야 한다는 조건을 공통 무결성 검사에 넣지 않는다.
대기시간, 픽업 거리, 공차 거리, 처리량과 예측 오차는 비교 결과로 기록하고 개선·악화의
원인을 해석한다.

현재의 3×3 맵과 고정 합성 호출은 초기 MVP 회귀 fixture로 남길 수 있지만, 다음 단계의
통합 완료 조건은 새 기능 범위와 설정에 맞춰 별도로 작성한다.

## 8. 완료 기록

통합 검사 결과에는 다음을 남긴다.

- 검사한 기능 범위와 제외한 범위
- 사용한 시나리오와 설정
- 실행한 자동 테스트와 결과
- 발견된 계약 불일치 또는 알려진 제한
- 정책 비교 지표와 해석
- 다음 단계에서 다시 확인할 항목
