# 프로젝트 공통 결정 기록

이 문서는 여러 모듈에 영향을 주는 미확정 사항과 확정된 주요 결정을 관리한다. 미확정 항목을 Agent가 독단적으로 프로젝트 표준으로 바꾸지 않는다.

## 1. 결정 상태

| 상태 | 의미 |
|---|---|
| 미확정 | 팀 또는 사용자의 결정이 필요함 |
| 임시 | 제한된 범위에서만 사용하는 가정이며 재검토가 필요함 |
| 확정 | 프로젝트 공통 기준으로 승인됨 |
| 폐기 | 더 이상 적용하지 않으며 대체 결정을 함께 기록함 |

## 3. 결정 원칙

- 여러 모듈에 영향을 주는 결정은 구현 전에 가능한 범위에서 합의한다.
- 임시 결정을 사용해야 하면 적용 범위와 되돌리는 비용을 기록한다.
- 결정은 선택한 대안뿐 아니라 선택 이유와 제외한 주요 대안도 남긴다.
- 결정이 바뀌면 기존 기록을 지우지 않고 상태와 대체 결정을 연결한다.
- 결정된 값은 관련 공용 문서, 코드, 설정과 테스트에 반영한다.
- 일정만을 이유로 데이터 유출, 계약 불일치 또는 재현성 문제를 허용하지 않는다.

## 4. 결정 기록 양식

새 결정은 최신 항목이 위에 오도록 아래 형식으로 추가한다.

```markdown

- 상태: 확정 | 임시 | 폐기
- 결정자:
- 배경:
- 결정:
- 근거:
- 검토한 대안:
- 영향받는 모듈과 문서:
- 호환성 또는 전환 계획:
- 재검토 조건:
```

## 5. 확정된 결정

### 2026-10-29 — `main`과 `develop` 브랜치 운영

- 상태: 확정
- 결정자: 사용자
- 배경: 안정 상태와 개발 통합 상태를 분리하여 여러 모듈의 병렬 작업을 관리할 필요가 있다.
- 결정: `main`은 검증된 안정 상태와 배포·발표 기준으로 사용하고, `develop`은 기본 통합 브랜치로 사용한다. 일반 작업 브랜치는 `develop`에서 분기하여 `develop`으로 병합하고, 통합 검증이 끝난 변경만 `main`에 반영한다.
- 근거: 안정 기준과 진행 중인 통합 작업을 분리하여 `main`의 신뢰성을 유지한다.
- 검토한 대안: `main`만 사용하는 단순 GitHub Flow.
- 영향받는 모듈과 문서: 전체 저장소, `docs/git_workflow.md`, `docs/development_start_guide.md`.
- 호환성 또는 전환 계획: 초기 커밋을 `main`에 만든 뒤 같은 커밋에서 `develop`을 생성하고 두 브랜치를 원격에 게시한다.
- 재검토 조건: 정기 릴리스, 별도 배포 환경 또는 릴리스 브랜치가 필요해질 때 재검토한다.

### 2026-10-29 — Python 개발 환경과 초기 명령

- 상태: 확정
- 결정자: 사용자
- 배경: 저장소를 처음 받은 개발자가 같은 환경을 구성하고 기본 검증을 실행할 공통 절차가 필요하다.
- 결정: Python 3.13, `venv`, `pip`와 `pyproject.toml`을 사용한다. 개발 환경은 `python -m pip install -e ".[dev]"`로 설치하고 전체 테스트는 `python -m pytest`로 실행한다. 개발 테스트 의존성은 Python 3.13을 지원하는 `pytest>=9.2,<10`으로 관리한다.
- 근거: Python 기본 도구 중심의 단순한 환경으로 초기 진입 비용과 중복 설정을 줄인다.
- 검토한 대안: 별도 패키지 관리자 사용, `requirements.txt` 병행 관리.
- 영향받는 모듈과 문서: 전체 저장소, `pyproject.toml`, `.gitignore`, `AGENTS.md`, `docs/development_start_guide.md`, `docs/testing_and_evaluation.md`.
- 호환성 또는 전환 계획: 첫 커밋부터 적용한다. Python 요구 버전이나 패키지 관리 방식을 바꾸면 환경 재생성 절차를 함께 갱신한다.
- 재검토 조건: 의존성 잠금, 배포 패키지 또는 별도 환경 관리 도구가 필요해질 때 재검토한다.

### 2026-10-29 — Git 브랜치와 커밋 컨벤션

- 상태: 폐기
- 결정자: 사용자
- 배경: 첫 커밋 전에 모듈별 협업과 변경 이력을 일관되게 관리할 최소 규칙이 필요하다.
- 결정: 단순한 GitHub Flow를 사용한다. 브랜치와 커밋은 영문 `type`과 `scope`를 사용하고, 커밋 제목과 본문은 한국어를 허용한다. 하위 디렉터리의 `AGENTS.md`는 해당 범위에 적용되는 세부 컨벤션을 별도로 정할 수 있다.
- 근거: 저장소 전체의 기본 형식을 통일하면서 모듈별 작업 방식의 자율성을 허용한다.
- 검토한 대안: 컨벤션 없음, 복잡한 GitFlow, 모든 모듈에 완전히 동일한 세부 규칙 강제.
- 영향받는 모듈과 문서: 전체 저장소, `AGENTS.md`, `docs/git_workflow.md`.
- 호환성 또는 전환 계획: 아직 커밋이 없으므로 첫 커밋부터 적용한다.
- 재검토 조건: 릴리스 브랜치가 필요해지거나 병렬 개발 규모가 커질 때 재검토한다.
- 대체 결정: `2026-10-29 — main과 develop 브랜치 운영`

### 2026-10-29 — 저장소 Skill의 위치와 이름 규칙

- 상태: 확정
- 결정자: 사용자
- 배경: 각 모듈에서 여러 Codex Skill을 만들 때 이름 충돌과 적용 범위 혼동을 방지할 공통 규칙이 필요하다.
- 결정: Skill 하나마다 독립된 디렉터리와 `SKILL.md`를 둔다. 디렉터리 이름과 `SKILL.md`의 `name`은 담당 모듈에 따라 `module1-`, `module2-`, `module3-`, `module4-` 접두사를 사용한다. 여러 모듈에 공통인 Skill은 `common-` 접두사를 사용한다.
- 근거: Skill의 소유 범위를 이름만으로 식별하고 서로 다른 위치의 동명 Skill이 선택 목록에 중복되는 것을 예방한다.
- 검토한 대안: 접두사 없이 기능명만 사용, 모든 Skill을 저장소 루트에만 배치.
- 영향받는 모듈과 문서: 모든 모듈의 `.agents/skills`, `AGENTS.md`, `docs/skill_authoring_guide.md`.
- 호환성 또는 전환 계획: 새 Skill부터 적용하며 기존 Skill이 생기면 같은 규칙에 맞춰 이름을 검토한다.
- 재검토 조건: 모듈 구조가 변경되거나 Skill을 플러그인으로 배포할 때 재검토한다.

Python 버전, `pytest` 및 GitHub Actions처럼 이미 `AGENTS.md`에서 확정한 공통 도구는 해당 문서를 기준으로 한다.
