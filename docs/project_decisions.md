# 프로젝트 공통 결정 기록

이 문서는 여러 모듈에 영향을 주는 미확정 사항과 확정된 주요 결정을 관리한다. 미확정 항목을 Agent가 독단적으로 프로젝트 표준으로 바꾸지 않는다.

## 1. 결정 상태

| 상태 | 의미 |
|---|---|
| 미확정 | 팀 또는 사용자의 결정이 필요함 |
| 임시 | 제한된 범위에서만 사용하는 가정이며 재검토가 필요함 |
| 확정 | 프로젝트 공통 기준으로 승인됨 |
| 폐기 | 더 이상 적용하지 않으며 대체 결정을 함께 기록함 |

| 항목 | 상태 | 주요 영향 |

## 3. 결정 원칙

- 여러 모듈에 영향을 주는 결정은 구현 전에 가능한 범위에서 합의한다.
- 임시 결정을 사용해야 하면 적용 범위와 되돌리는 비용을 기록한다.
- 결정은 선택한 대안뿐 아니라 선택 이유와 제외한 주요 대안도 남긴다.
- 결정이 바뀌면 기존 기록을 지우지 않고 상태와 대체 결정을 연결한다.
- 결정된 값은 관련 공용 문서, 코드, 설정과 테스트에 반영한다.
- 일정만을 이유로 데이터 유출, 계약 불일치 또는 재현성 문제를 허용하지 않는다.

### 2026-11-01 — 개발용 호출을 한 명씩 연속 발생

- 상태: 임시(개발 시연 전용)
- 결정자: 사용자(6건 묶음 반복 제거 요청), Agent(초기 호출 간격 5초)
- 결정: 시작 시각 0부터 기본 5 시뮬레이션 초마다 손님 한 명을 발생시킨다. 그 순간 16개 교차로에서 서로 다른 출발·도착을 무작위로 뽑는다. 호출 수 제한이나 묶음·회차 개념을 사용하지 않는다.
- 설정: `configs/module1_calls.toml`의 `interval_seconds`, `seed`. CLI로 간격·시드를 덮어쓸 수 있다. R 초기화 시 시드·호출 번호·운행 상태를 초기화한다.
- 범위: Module 1 개발 화면의 입력에 한정한다. Simulation의 외부 시나리오 적재 API와 Module 2 역할은 그대로 유지한다.
- 호환성: 기본 실행에서 샘플 JSON과 반복 재생 옵션을 제거한다. 기존 6건은 유한 시나리오 회귀 테스트 fixture로 옮기고 기본 실행에서 읽지 않는다.
- 재검토 조건: 호출 간격 조정 또는 Module 2 시나리오 연결 시.

### 2026-10-31 — 운행 확인용 FIFO·가까운 빈 택시 연결

- 상태: 임시(개발 시연 전용)
- 결정자: 사용자(‘호출 순서대로 가장 가까운 빈 택시 연결’ 선택)
- 결정: 기본 실행에서 사전 고정 택시·호출 연결을 제거한다. 발생한 배차 대기 호출을 발생 시각·호출 ID 순으로 처리하고 현재 빈 택시 중 도로 거리 최솟값을 선택한다. 거리 동률은 택시 ID 순서로 해결한다. 빈 택시가 없으면 다음 tick에 다시 시도한다.
- 범위: Module 1 운행 확인용 `DemoRunner`에 한정한다. `Simulation.dispatch()`는 외부에서 지정한 명령만 실행하며, Module 4 정식 정책·재배치·최적화는 구현하지 않는다.
- 호환성: 고정 연결 파일은 회귀 테스트 fixture로 옮기고 기본 실행에서 읽지 않는다. 수동 모드는 유지한다.
- 재검토 조건: Module 4 담당자의 정책을 연결할 때 개발용 연결기를 대체한다.

### 2026-10-31 — 개발용 호출 위치 무작위화

- 상태: 임시(개발 시연 전용)
- 결정자: 사용자(호출 위치 무작위화 요청)
- 결정: 기존 호출 시각은 유지하고 매 호출의 출발·도착을 16개 교차로에서 서로 다르게 균등 추출한다. 전용 난수 시드로 재현하고 반복 회차에서도 새 위치를 추출한다.
- 범위: Module 1 화면 확인용 시연 입력에만 적용한다. Module 2의 학습·평가용 시나리오 생성이나 실제 수요 모델을 구현하는 결정이 아니다.
- 영향: 기본 실행·수동 모드·반복 시연. Simulation에 직접 전달한 시나리오의 좌표는 변경하지 않는다.
- 시연 처리: 기존 파일에 지정된 택시·호출 연결은 유지한다. 지정 택시가 운행 중이면 시연 명령을 보류하고 대기 상태가 되었을 때 실행한다. 택시 선택 정책은 추가하지 않는다.
- 재현: `--seed`로 위치 난수만 제어하고 R 초기화 시 같은 위치 순서를 재생한다. `--fixed-locations`로 기존 고정 위치를 재생할 수 있다.
- 재검토 조건: Module 2 호출 시나리오 생성기 연결 시 개발용 입력을 대체한다.

### 2026-10-31 — Module 1 호출·운행·재배치 경계

- 상태: 임시
- 결정자: 사용자(호출→픽업→탑승→하차·재배치 실행과 기록의 구현 범위 승인), Agent(구현에 필요한 임시 세부 규칙)

- 후속 정정: 같은 날짜의 ‘현재 Module 1 범위를 차량·승객 운행으로 제한’에 따라 재배치 관련 구현과 계약은 철회한다.

### 2026-10-29 — `main`과 `develop` 브랜치 운영

- 상태: 확정
- 결정자: 사용자
- 배경: 안정 상태와 개발 통합 상태를 분리하여 여러 모듈의 병렬 작업을 관리할 필요가 있다.
- 결정: `main`은 검증된 안정 상태와 배포·발표 기준으로 사용하고, `develop`은 기본 통합 브랜치로 사용한다. 일반 작업 브랜치는 `develop`에서 분기하여 `develop`으로 병합하고, 통합 검증이 끝난 변경만 `main`에 반영한다.
- 근거: 안정 기준과 진행 중인 통합 작업을 분리하여 `main`의 신뢰성을 유지한다.
- 검토한 대안: `main`만 사용하는 단순 GitHub Flow.
- 영향받는 모듈과 문서: 전체 저장소, `docs/git_workflow.md`, `docs/development_start_guide.md`.
- 호환성 또는 전환 계획: 초기 커밋을 `main`에 만든 뒤 같은 커밋에서 `develop`을 생성하고 두 브랜치를 원격에 게시한다.
- 재검토 조건: 정기 릴리스, 별도 배포 환경 또는 릴리스 브랜치가 필요해질 때 재검토한다.
